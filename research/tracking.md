# Tracking and maintenance

## Snapshot and coverage

The initial audit began November 8, 2026, in San Francisco time. Every club in the current inventory has an audit entry; subsequent checks and their limits are recorded individually in each club's `research_log`. The event file is a selection of dated listings found in accessible sources, focused on November 9–22, 2026 plus some later events. Some organizer event cards were inspected using a signed-in Strava session; only event details and stable links are stored, not account information or credentials. It is **not** exhaustive across all calendars or every future occurrence. Recurring schedules and historical profiles cannot establish a dated event. Many Instagram, Strava and Meetup details were unavailable or require sign-in; source access describes the recorded check, not a guarantee of current availability.

## Where each fact lives

Each fact is stored once; the validator rejects unknown fields so copies cannot creep back.

- `clubs.json`: who a club is (name, the requested name, geography) and its runner-facing `description`.
- `audits.json`: what we know about each club and when: `result`, `checked_on`, `review_due`, research `notes` and `research_log`. Its `reference_source_ids` list the club's sources; the first is the club's primary source.
- `sources.json`: one record per page (each URL once) with its `authority`, `roles`, `access` and `last_checked`. Every source must be cited by an audit, regular run or dated run. Records cite sources by ID and never copy their fields.
- `schedules.json` and `events.json`: regular and dated runs. `run_details.sources` and `run_details.checked_on` are stored only when the details come from a different page or check than the run's own `source_id` and `checked_on`.
- Allowed values for every enumerated field are defined once in [`scripts/vocabulary.mts`](../scripts/vocabulary.mts).
- The RSS feed (published dated club runs only, including past listings) and the club CSV are built from these files when the site deploys and are not committed. `npm run schedule`, `npm run report` and `npm run review` print other views on demand.

## Updating safely

1. Start with `audits.json`, order by `review_due`, and open the organizer's event channel in `sources.json`. Review upcoming dates, precise meeting point, registration, price and cancellation updates. Search for an organizer channel if only a third-party directory is known.
2. Add or update a source with a stable `src-` ID, reusing the existing record if its URL is already there; keep authority and access honest. `last_checked` means a page was inspected, not that its contents are current. Capture source publication dates or the event date in notes where known; a recently visited old page is still old.
3. Update the club's audit notes, check date and review date. Keep the club's primary source first in `reference_source_ids`. Keep unknowns and conflicting accounts explicit. Do not treat a failed login, absent listing, or stale page as evidence of inactivity.
   Append a `research_log` entry to the audit: `checked_on`, `summary`, actionable `next_steps`, and `source_checks` with a `source_id`, `method`, and source-specific `notes`. The method is `page` for an inspected page, `search_result` for a search snippet or cached result, `restricted` when sign-in or access restrictions blocked inspection, `unavailable` for retrieval failures such as timeouts, cache misses or HTTP errors, `not_checked` for a lead to investigate, or `not_recorded` if the method was not captured. The date is when the research was done, not the date the source was published. Source checks can be empty if the pass found no usable source. Every checked source must also be in the audit’s `reference_source_ids`, and an entry’s date cannot be later than the audit date. A retrieval failure alone does not establish that a club is inactive or a page has been deleted. Keep previous entries so future research can trace what was checked and why; never include private credentials.
4. Add a `schedules.json` pattern only for an explicit source statement. Preserve the exact frequency and any date bounds; use null when time is unknown. A pattern is a lead and must not be expanded into claimed events. For special seasonal schedules set both `valid_from` and `valid_until` when known.

5. Add `events.json` records only for individually dated listings supported by a source. Use `published` for a dated listing found in a source and `unconfirmed` for a dated lead that needs verification. Set optional `needs_review: true` for an unresolved detail or conflict and explain it in notes; a fresh check alone does not clear the flag. Use `unconfirmed` when the event itself or a critical detail such as its meeting place is uncertain. Store local date/time and IANA time zone, source ID, precise location as stated, and a note when any detail is unknown or contradictory. Write `notes` for a runner, in plain words: what to expect and what to check. Keep evidence detail (which page or card showed what, access methods, source conflicts, retrieval failures) in the optional `research_notes`, which the site shows collapsed and the feed leaves out. Club `description`s follow the same rule; research caveats about a club belong in its audit notes. Use a stable ID per club, source event and start; don't duplicate the same event from multiple aggregators. Record cancellation or postponement and recheck date changes instead of silently deleting history. Never infer an event's location from a different occurrence.
   Optional `run_details` holds documented distance options (`label`, `min_miles`, `max_miles`, with null maximum for open-ended distances), pace, beginner/no-drop status, cost, RSVP and access. Add `sources` and `checked_on` only when the details come from a different page or check than the run itself; omit unknown facts rather than inventing them. The distance filters match any overlapping documented option, so discrete routes should be separate options. Optional `location_info` can record broad `area` (`sf`, `marin` or `bay`), a neighborhood label listed in `data/neighborhoods.json` (see [neighborhoods.md](neighborhoods.md)) and a `directions_query` for a sufficiently precise meeting point. Leave these fields absent when location is unclear or rotates, and do not geocode a guessed address.
6. Run `npm run verify`. Validation rejects duplicate and unknown JSON fields, which could otherwise silently overwrite or copy source details. Inspect `npm run report -- --club 'name'`, and check that each source supports the changed claim before opening a pull request.

The initial `review_due` of November 22 is a reminder to recheck, **not** a guarantee that any event remains valid until then. Faster-changing club events should be checked closer to the run. Every Monday, the workflow opens or updates a *Research review due* issue. `npm run review -- --within 7` generates the same queue locally; `--as-of YYYY-MM-DD` makes a historical or future run reproducible. The queue includes:

- Club audits and active patterns due within seven days, plus patterns flagged `needs_review` immediately even if their review date is later. Expired or superseded patterns do not create reminders, though a club's own audit can still be due.
- Published and unconfirmed runs on the local calendar date through 14 days ahead, if flagged `needs_review`, unconfirmed, missing a check date, or the check is or will be 14 days old by the earlier of the run or next weekly reminder. Open the linked source and review cancellations, changed start times and meeting points, and other details. A stale check is a prompt, not proof of a change; a recent check is not a guarantee or a reason to clear an unresolved flag.
- Clubs without a published dated run in that 14-day window. These are coverage gaps, not evidence that a club is inactive. The queue links recorded channels and identifies their authority and access limitations. Search for other current organizer sources as needed; never promote a recurring pattern into a dated event without evidence.
- Scheduled races within 30 days (or in progress) that are flagged or whose source check becomes 30 days old by the earlier of race day or the next weekly reminder. See `research/races.md` for details.

The windows are independent of `--within`, which changes only the club review horizon. The issue stays open while any club, run or race needs a check and closes when none does; coverage gaps are listed but do not keep it open. A long queue is shortened to fit GitHub's issue size limit, and the local command prints it in full. It reads only committed data, never contacts sources or detects changes, and never edits data. Recheck sources and record the evidence before updating the snapshot; consider a same-day cancellation check before featuring a run. No scraping or automated refresh is enabled.

## Status vocabulary

- `dated_event_found`: at least one dated event was captured during this pass; not a completeness or real-time guarantee.
- `pattern_found`: only a recurring pattern was recorded, with its provenance and limits.
- `no_current_details`: no usable pattern or dated event was captured; the club may still be active.
- `identity_unresolved`: the supplied name has not been matched reliably to a particular organization.

Club-controlled sources are preferred for schedule and location. Host event pages are strong for a hosted event. Directory claims are useful leads but can be stale, omit exceptions, merge distinct groups or mistake East Bay for SF. Keep a link to all evidence, and separate organizer-controlled update channels from secondary discovery sources. Review each claim before publication rather than copying whole directories.

## Viewing the data

`npm run schedule -- --days 45` prints an upcoming-schedule table and `npm run report -- --include-patterns --include-unconfirmed` shows possible dated candidates separately from published listings. Both are printed on demand rather than committed, because a stored copy goes stale as soon as the JSON changes. Report candidates cannot know about cancellations or exceptions; never turn them into confirmed records without a dated source.

## Attendance labels

Optional `run_details.meeting_point` is `listed`, `pending`, `after_registration` or `members_only`; an address shared after registration is different from an unresolved location. `participation` is `open`, `registration_required`, `approval_required`, `members_only` or `waiver_required`. Like other run details, labels share the run's own source and check date unless `run_details` records different ones. Absence means unknown. A run whose meeting point is still `pending` stays `unconfirmed`; the validator enforces this.
